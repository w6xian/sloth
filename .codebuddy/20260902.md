# sloth/v4 项目分析报告

## 一、现状基线

| 检查项 | 结果 |
|---|---|
| `go build ./...` / `go vet ./...` | 通过 |
| `go test ./...` | 通过（bucket / decoder / message / utils / bench） |
| 架构亮点 | 协议工厂抽象（`ProtocolFactory`）+ `nrpc.Transport` 接口、bucket 分桶 + 房间/通道分层、手写单次分配 TLV Header 编码器（~464B/11 allocs → 单次分配）、FN/AG 双解码器、FrameRouter 协议无关路由 |

结论：分层清晰、扩展点已预留，但**核心链路存在一个致命缺陷，且多处"半成品"配置未落地**。

## 二、问题清单（按优先级）

### P0 — 致命/功能性缺陷（必须修复）

**1. `Serve()` 的 HTTP handler 与 mux 路由完全脱节 → WebSocket 实际无法建立连接**

```256:256:connect.go
if err := http.Serve(listener.Listener, nil); err != nil {
```

`http.Serve` 传 `nil` handler 会使用 `http.DefaultServeMux`；而 `serveWs`/`OnConnect` 校验注册在 `WsServer` 自己的 `mux.NewRouter()` 上（`ws_server.go:99,173`），从未挂载到任何 server。同时 `ListenAndServe`（`ws_server.go:167-186`）只注册路由、不真正监听，`initWsServerInstance` 返回的 error 在 `factory.go:20` 被忽略。

后果：所有 WS 请求 404，`OnConnect` 鉴权、origin 校验、`serveWs` 全部失效；`wss` 分支 `Handler: nil` 同样问题；多个 ws listener 也只会初始化一个 `WsServer` 实例。

**修复方案**（推荐 A）：
```go
// ws_server.go: WsServer 暴露 handler
func (s *WsServer) Handler() http.Handler { return s.router }

// connect.go: Serve() 使用 wsServer.Handler()
if err := http.Serve(listener.Listener, wsServer.Handler()); err != nil { ... }
// wss: srv := &http.Server{Handler: wsServer.Handler()}
```
并让 `ListenAndServe` 真正 `http.Server.Serve(ln)`，或删除它、统一由 `Serve()` 驱动，避免双入口。

**2. `Dial` 未知协议静默降级为 WebSocket，且地址不带 scheme**

```360:371:connect.go
default:
	c.Log(logger.Info, "unknown network type: %s, using WebSocket", network)
	opts := []option.ConnectOption{
		option.WithUriPath("/ws"),
		option.WithAddress(address),   // ← 无 ws:// 前缀，连接地址错误
	}
```

`WithAddress(address)` 缺少 scheme 前缀，即使降级也连不上；静默降级掩盖配置错误。应改为 `return fmt.Errorf("unsupported network type: %s", network)`，与 `Listen` 行为一致。

### P1 — 重要可靠性问题

**3. 心跳间隔硬编码，忽略配置**

```242:242:nrpc/wsocket/ws_server.go
ticker := time.NewTicker(9 * time.Second)
```

`NewWsServer` 已保存 `s.PingPeriod`（默认 54s），此处应改用 `s.PingPeriod`。否则配置 `WithPingPeriod` 无效，且 9s ping 与 PongWait 默认值的关系需重核。

**4. `GetCodecer` 空包 panic**

```24:32:internal/codec/codec.go
func GetCodecer(raw []byte) (Codec, error) {
	prev := raw[0]
	proto := raw[1]
```

网络字节流不可信，`raw` 为空或长度 < 2 时索引越界 panic。入口应加 `len(raw) < 2` 保护（参考 `NewHeaderFromBV` 已有 panic 兜底的先例）。

**5. 优雅关闭缺失**

`Connect.Close()`（`connect.go:302-318`）只关闭 listener，不关闭：活跃 WebSocket 连接、bucket worker 池、`http.Server`（`http.Serve` 无法被 ctx 取消）。长期运行的服务在滚动发布/重启时会泄漏连接与 goroutine。建议：
- `WsServer` 维护活跃连接集合并暴露 `Close()`（关闭所有 channel + `ch.broadcast`）
- `Serve()` 改为 `Shutdown(ctx)` 支持优雅退出（`http.Server.Shutdown` + worker 排空）

**6. `serviceMap` 无锁**

`Register`（写，`connect.go:170`）与 `IsRegisteredService`/`CallFunc`（读，`connect.go:99,391`）并发无保护。注册通常在启动期，但 `IsRegisteredService` 可能在运行期被反复调用，建议加 `sync.RWMutex` 或 `sync.Map`。

**7. Options 半成品字段**

`MaxConnsGlobal/PerIP/WS/TCP/KCP`、`AutoBan*`、`TrustProxyHeaders` 全部定义未实现。二选一：实现（配合 `serveWs` 升级前的计数 + 封禁 map），或**移除**——保留会误导使用者以为有防护。

### P2 — 性能与健壮性优化

**8. `Room.Each/Range/EachBatch` 每次全量快照分配**

`Room.Broadcast` → `Each` 是广播热点，每次 `make([]IChannel, 0, len(...))` O(n) 分配。设计注释已说明"先快照后回调"是为了回调内可安全 Join/Leave。折中方案：增加 `EachLocked`（持读锁回调，文档明确要求 fn 不得调用 Join/Leave），供 `Broadcast` 这类纯只读场景使用，消除分配；或复用 `sync.Pool` 快照缓冲。

**9. `RpcChannel.Call` header 引用随池对象复用**

```46:51:nrpc/conn.go
msg := message.GetCallJCO()
msg.Header = header
...
message.PutCallJCO(msg)
```

`Serialize` 同步完成所以无并发污染，但 `PutCallJCO` 后 `msg.Header` 仍指向调用方 map，池对象下次取出时可能残留旧引用。防御性修复：`GetCallJCO` 重置 `Header = nil`（与 `GetHeader` 的清空逻辑保持一致），并核对 pool 实现。

**10. `bytes_to_*` 非法长度静默返回 0**

`internal/ref/conv.go`：长度非 1/2/4/8 的字节序列直接返回 0，参数错误被吞掉。建议返回 error 或由调用方校验，避免把"参数被截断"伪装成"合法值 0"。

**11. `utils.AnyToBytes` 对 `[]byte` 额外拷贝**（低优先级，命中热路径时可改为类型断言零拷贝）

## 三、多协议扩展准备（为 TCP/QUIC/KCP/gRPC 铺路）

现状：`ProtocolFactory`/`nrpc.Transport` 接口已定义，但只有 `wsProtocolFactory` 一个实现，且 `Listen`/`Dial`/`Serve` 对非 ws 协议全部拒绝。落地路径：

1. **以 `ProtocolFactory` 为唯一分发入口**：`Listen(network, addr)` → `factory.Listen(ctx, addr)` 返回 `ProtocolListener`；`Serve()` 遍历 listener 调 `factory.Serve(l)`；`Dial` 调 `factory.Dial(ctx, addr)`。删除 `connect.go` 里散落的 `switch network` 分支（`resolveProtocol` 已具备该骨架）。
2. **补全 ws 的 `nrpc.Transport` 适配**：参考 `nrpc/transport.go` 中已注释的 `WsTransportAdapter` 思路，让 ws 协议走统一 Transport 接口（`Send`/`Recv`/`Close`），`RpcChannel` 只依赖 Transport，不依赖 gorilla/websocket 具体类型。
3. **帧路由已就绪**：`internal/transport/dispatch.go` 的 `FrameRouter.DispatchMessage` 是协议无关的，新协议只需注册 codec + transport，路由层无需改动。注意 `NewFrameRouterWithCodec` 每次调用新建 router，建议单例复用。
4. **编码器可插拔**：`codec.Codec` 接口（Detect/Decode/Encode）已通用，新协议实现该接口即可接入 `DispatchMessage`。
5. **约定职责边界**：bucket/room/channel 层已完全协议无关，新协议只动 `nrpc/wsocket` 同级目录 + `factory.go` + `connect.go` 分发。
