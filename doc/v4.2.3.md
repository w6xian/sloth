# sloth v4.2.3

一次业务侧排障引出的发版：回单 PDF 走 RPC 正文时调用直接失败——

```
{code: 502, message: "调用注册服务失败: ag: data length exceeds 65535"}
```

AG 帧的长度字段只有 2 字节，**单帧 Value 上限写死 65535**，没有任何配置项可绕。
本版给 AG 加扩展帧，把**协议上限抬到 1GB**（与 fn 帧对齐）。

协议只决定"能表达多大"；"这一侧收多大"是部署策略，用 `sloth.WithMaxParamSize`
按连接设——协议不该替业务做这个决定：协议写小了，想传大包的合法场景就永远没门。

## 新增

### 1. 扩展帧：LEN 写满值作转义位

```
短帧（Value ≤ 65534）——与旧格式逐字节一致
  MAGIC  :p   2 byte   0x3A 0x70（ASCII ":p"）
  TYPE   t    1 byte   ArgumentType* 枚举
  LEN    l    2 byte   big endian，Value 字节数（0 ~ 65534）
  VALUE  d    l byte

扩展帧（Value ≥ 65535）——真实长度跟在转义位后面
  MAGIC  :p   2 byte
  TYPE   t    1 byte
  FLAG       2 byte   固定 0xFFFF
  LEN32  n   4 byte   big endian，Value 字节数（65535 ~ 1GB）
  VALUE  d   n byte
```

**为什么不新增 type 标签**：type 是既有语义（Bytes / String / Slice…），老端碰到未知 tag 的
行为不确定；让出 `0xFFFF` 则 type 一词不动、短帧格式一词不动，未升级的对端照样收发小包。
代价是短帧上限从 65535 降到 65534。

### 2. 限制按连接设：`WithMaxParamSize`

```go
server := sloth.DefaultServer(sloth.WithMaxParamSize(4 << 20))
client := sloth.DefaultClient(sloth.WithMaxParamSize(4 << 20))
```

- 入站：长度字段超过它直接拒绝，**不照对端声明的数字分配内存**（一个声明 4GB 的帧
  打不爆内存，也不会被当成合法帧透传）；
- 出站：编码阶段就报错，不会发出去白跑一趟再被对端拒；
- **只设一侧也生效**：入站与出站走的是两个 rpc 对象，建连接时会把设过的值同步过去，
  只设一个不会漏掉一个方向；
- 下限是 1 而不是 65535：想收得比 65535 更紧（公网入口只收几 KB）是合理诉求；
- 不设则沿用协议上限 1GB——传大包**不需要任何声明**。

`ag.SetMaxDataSize(n)` 保留为**进程级兜底**，只在没按连接设时生效。它是一刀切：
同一个进程里既有可信内网监听、又有公网入口时，没法给两者不同值，那种场景请用
`WithMaxParamSize` 建两条 Connect。

JS 侧（`examples/ws/web`）同步：`AG.NewEncoder(n)` / `AG.NewDecoder(n)` /
`AG.SetMaxDataSize(n)`，帧格式与 Go 端逐字节对齐。

### 3. 走 ws 时的第二道闸

ws 还有 `option.WithMaxMessageSize`（默认 1MB，`option/options.go`）。AG 抬到 1GB
不代表 ws 能收 1GB：单包超过 1MB 要先抬它，否则卡在 ws 层。
tcp / quic / kcp 的 fn 帧长度是 uint32（1GB），没有这层限制。

## 修复

### 1. JS 端上限差一（会静默丢数据）

原值 `ArgumentMaxDataSize = 1 << 16`（65536）：`encode_ag` 会接受 65536 字节的 Value，
再被 2 字节长度截断成 0——**编出长度 0 的帧，数据静默丢失**，不报错。
对齐 Go 端改为 65535（现名 `LegacyMaxDataSize`）。

### 2. `Decoder` 对"有 magic 却解析不了"的帧改为报错

此前 `IsArgument` 判否就走"非 AG 帧"分支，把**带帧头的原始字节**原样透传。
典型场景是对端发的帧超过本侧限制：解不开却被当成业务数据交上去，是静默错数据。
现在先检查 magic，命中却解析失败就返回明确错误。

### 3. `DecodeArgs` 不再吞掉解码错误

`decoder.DecodeArgs` 原实现失败时把原始字节**原样塞回**参数列表
（`a = append(a, v); continue`），于是上面那条"明确报错"到了 RPC 层又被吞掉：
带帧头的字节照样喂给反射调用。现在任一个参数解不开，整个调用直接返回错误。

### 4. 解析侧先校验长度再分配

长度由对端给出，原实现照着分配：一个声明 4GB 的帧就能打爆内存。
现在先按当前限制校验，超限直接拒绝；比较放在 `uint64` 域——32 位平台上
`int(uint32)` 可能溢出成负数绕过校验。短帧同样要比（限制设成 4KB 时，
一条 60KB 的短帧也得拒）。

### 5. 超长错误保留哨兵语义

限制恰好等于老上限（65535）时直接返回哨兵 `ErrAgDataTooLarge`，**连错误文本都与
原来一致**；其余情况附上实际值与当前限制并 wrap 哨兵——`errors.Is` 与按文本匹配的
调用方都认得。

## 兼容性

| 场景 | 结论 |
|---|---|
| 短帧 Value ≤ 65534 | 双向兼容，可混版本 |
| 扩展帧 | **只有两端都升级过才通** |
| Value 恰好 65535 | 从短帧变扩展帧，未升级的老端解不开（唯一不兼容的长度） |
| 不设 `WithMaxParamSize` | 协议上限 1GB 生效，传大包无需声明 |

## 升级注意

- **默认行为变了**：从"超过 65535 一律拒绝"变成"协议上限 1GB"。老版本能编的帧
  新版本照样能编，反向不成立——**老端收到扩展帧解不开**，所以大包链路两端都得升。
- 想保持旧行为（收紧到 65535）：`sloth.WithMaxParamSize(ag.LegacyMaxDataSize)`。
- **日志关键字**：限制不等于 65535 时，超长错误变成 `ag: data length exceeds N (got M)`；
  等于 65535 时仍是 `ag: data length exceeds 65535`，老 grep 规则不失效。
- **`DecodeArgs` 语义变更**：入参解不开时整个调用失败（此前静默透传带头字节）。
  有跨版本链路且一端没升时，这会把"静默错数据"变成"明确报错"——更容易发现，但会多出报错。
- 走 ws 且单包 >1MB，记得 `option.WithMaxMessageSize`。
- 无破坏性 API 变更：`Encode` / `Decode` / `Decoder` / `Validate` / `IsArgument` 签名均未变；
  `WithMaxParamSize` 走窄接口断言，不需要现有 `IRpc` 实现方改代码。

## 测试

- 边界：65534（短帧）/ 65535（扩展帧）、`ClampLimit` 夹取、`SetMaxDataSize(0)` 恢复默认
- `NewEncoder` / `NewDecoder` 按实例生效，且不影响进程级默认值
- 4MB Value 全链路往返（编码 → 解码 → 逐字节比对）
- 坏帧三类：帧截断、扩展帧头不足、声明 4GB（既不分配内存也拒绝）
- 老端短帧兼容、非 AG 帧透传
- e2e（tcp 全链路）：`WithMaxParamSize(4MB)` 下 1MB 入参走完整 RPC；
  限制收紧到 1KB 后超限入参在出站被拒；只设一侧时另一侧同步生效
- JS 端同一套用例在 bundle 与 min 版本各跑一遍

## 后续（未实现）

- **分片 / 流式调用**：抬上限只是把天花板推高，本质仍是"整包进内存"。真要传几百 MB
  的扫描件，需要 `CallStream` 之类的分块接口——但 sloth 的反射调用按方法签名传参，
  加这类接口两端都要改，还要引入顺序与幂等状态。更省事的绕法一直是**传地址不传内容**
  （文件路径 / URL，让服务端自己读）。
- **按连接设上限的指标化**：超长被拒目前只体现在错误里，没有计数器；跨语言链路排障时
  "哪一侧的限制更小"只能靠猜。
- **ws 侧自动跟随**：`WithMaxMessageSize` 与 `WithMaxParamSize` 现在是两条独立配置，
  前者小于后者时，AG 抬得再高也过不去 ws 层——可以让 ws 在没显式设时按 param size 推导。
