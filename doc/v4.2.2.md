# sloth v4.2.2

一次线上排障引出的发版：日志里同一毫秒冒出 7 条 `ERR trace=- msg="server readPump，ch.conn.ReadMessage return"`，
既没有错误内容也没有 trace，无法定位。查下来是**读循环把"正常断连"统一当 ERROR 刷**，
且日志出口传的是 `nil` ctx（`trace=-` 的根源）。本版把三条传输的断连日志都按原因分级，
并顺手把 ws 侧一个"注册了永不触发"的连接级钩子接进读循环。

## 修复

### 1. ws / wss：断连日志按原因分级（服务端 + 客户端）

`wsocket` 的 readPump 原来这样处理 `ReadMessage` 的返回：

```go
if websocket.IsUnexpectedCloseError(err, websocket.CloseGoingAway, websocket.CloseAbnormalClosure) {
    // 真异常 → OnError → return（反倒没有任何日志）
} else {
    // OnClose
}
s.log(logger.Error, "server readPump，ch.conn.ReadMessage return")  // 日常断连全从这里刷 ERR
```

关键在 `IsUnexpectedCloseError` 的语义：**它只对"非期望 code 的 `*websocket.CloseError`"返回 true**，
`EOF`、读超时（`i/o timeout`）、连接重置这些**最常见的断连全部落在 else 分支**。于是：

- 每次客户端正常下线都刷一条 ERROR；
- 真异常那支反而静默 `return`，什么都不记；
- `err` 本身没进日志，看不出是 EOF 还是超时；
- `s.log()` / `c.log()` 内部是 `logger.Logf(level, nil, ...)`，**传 nil ctx** → `trace=-`，
  连连接建立时 `WithFields(ctx, "ip", ip)` 挂上的 ip 一起丢。

现在按分支定级别，并把 `ctx` 与原始错误带上：

```go
if websocket.IsUnexpectedCloseError(...) {
    if s.handler != nil { s.handler.OnError(ctx, r, s, ch, err) }
    logger.Errorw(ctx, "server readPump closed unexpectedly", "err", err)
    ch.fireErr(err)
    return
}
if s.handler != nil { s.handler.OnClose(ctx, r, s, ch) }
logger.Infow(ctx, "server readPump conn closed", "err", err)   // 预期断开：降为 Info
return
```

客户端（`LocalClient.readPump`）同口径处理，并去掉了原来"先无差别 Errorw 一条、
再补一条无上下文 `c.log(Error, "…")`"的重复日志。

### 2. tcp / quic / kcp：共用读循环同样分级

这三条传输没有各自的读循环，全部收敛到 `nrpc/stream.RunPump`。原实现更粗：

```go
frame, err := ReadFrame(ch.reader, ch.head[:])
if err != nil {
    if ch.errHandler != nil && !errors.Is(err, net.ErrClosed) {
        ch.errHandler(err)   // 默认钩子 = logger.Errorw(nil, "stream channel error", "err", err)
    }
    return
}
```

只排除了"本端主动关闭"，`EOF` 与读超时照样走默认钩子 → 每条连接断开一条 `ERR stream channel error`，
而且**没有 ctx、没有 remote**，比 ws 那条更难定位。

现在：

- `net.ErrClosed`（本端主动 Close）→ 静默返回，不回调；
- `isExpectedDisconnect(err)`（`io.EOF` / `io.ErrUnexpectedEOF` / `net.Error.Timeout()`）→ `Infow`，带 `remote`；
- 其余（magic 错、length 超限、connection reset）→ `Errorw`，带 `remote`；
- 默认 `errHandler` 改为**空实现**，避免与读循环重复打印；业务注册的 `OnError` 钩子行为不变。

字节流没有 close 帧，断连原因只能从 `err` 本身分辨——这也是判定函数只认 EOF 与超时的原因。

## 新增

### ws 连接级错误钩子：`ch.OnError`

`WsChannelServer` 一直有 `errHandler` 字段、默认实现和 `OnError(f)` setter，
但**全仓库没有调用点**——注册了永不触发；而 `stream.Channel` 的同名钩子是会触发的，跨传输不对称。

现在接进 ws 读循环，**触发范围刻意收窄**：

- 触发：非预期关闭、分帧/解码失败（`receiveMessage` 报错）；
- 不触发：对端主动 close、EOF、读超时（它们是预期断开，走业务的 `OnClose`——否则每次正常下线都回调一次）。

实现细节：

- 字段改为 `atomic.Pointer[func(err error)]`：读循环在 goroutine 上读，业务常在 `OnReady` 里注册，直接读写会被 `-race` 抓到；
- `OnError(nil)` 复位为默认（静默），调用点不必判空；
- 默认实现**不打印**：读循环已按级别打印带 trace / ip 的日志，默认若再打印就只能是 nil ctx，又会变回 `trace=-` 的 ERR。

契约（已写进 README 与代码注释）：钩子运行在读循环协程上，**不要阻塞**（会堵住这条连接的所有后续入站），
**不要在钩子里 `ch.Close()` 或改动 bucket 成员**（读循环的 defer 正在清理，重入即竞态）。

## 升级注意

- **日志文本变了**：`grep "ReadMessage return"` / `grep "stream channel error"` 会失效。
  新的关键字是 `conn closed`（预期断开，INF）与 `closed unexpectedly` / `readPump failed`（真异常，ERR）。
- **日志量会明显下降**：正常断连从 ERR 降为 INF，需要"断连即告警"的监控规则要改成盯 ERR 关键字而不是盯级别。
- **排障反而更容易了**：预期断开也保留 `err=` 原文，判断"批量读超时"还是"客户端正常下线"看 `err` 即可
  （`EOF` / `i/o timeout` 是最常见的两种）。
- ws 侧若业务注册过 `ch.OnError`：此前**从不触发**，升级后会在真异常上触发——请确认钩子实现幂等且不阻塞。
- 无破坏性 API 变更：`OnError`、`OnClose`、`IsClosed` 等签名均未变。
