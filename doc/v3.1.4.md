我建议把它拆成 4 层，而不是继续在一个 `Connect` / `WsServer` 里混着写。

1. 传输层
2. 编解码层
3. 分发层
4. 连接/会话/桶房层

这样以后增加 `tcp`、`quic`、`kcp` 时，只扩展对应协议实现，不需要改业务代码。

我先说结论：是的，完全可以抽象出连接层，并且你现在的思路“只保留 ws，统一走 @FN 还是 Data fallback”是合理的，而且比现在这种架构更清晰。

我建议的核心结构

- `Connect` 只保留“应用入口”
  - 注册服务
  - 绑定客户端/服务端运行时
  - 选择协议工厂
  - 启动监听/连接

- `Transport` 负责“收发字节”
  - WebSocket 只实现一个 `Transport`
  - 以后再加 tcp/quic 时只加实现

- `Codec` 负责“字节 -> 帧 -> 业务对象”
  - `fn` 作为默认 codec
  - 识别 `@FN` 还是普通 `Data`

- `Dispatcher` 负责“帧分发”
  - 若是 `@FN`：
    - `ACTION_CALL` -> 查本地注册服务
    - 本地没有 -> 转 `CallNetFunc`
    - 绑定成功 -> 走 `CallFunc`
  - 若不是 `@FN`：
    - 直接走 `handler.OnData(...)`

- `Session` / Bucket / `Room`
  - 连接实例属于 transport 层
  - Bucket/Room 属于连接管理层，不属于 transport 细节

你现在的业务方向其实基本就是这个：

- 服务端/客户端都绑定方法
- 工厂创建连接
- 解包
- `@FN` 走 RPC
- 非 `@FN` 走 `OnData`
- 用户连接用 Bucket / `Room`

这套思路很对，问题不是思路，而是当前实现把“协议栈”和“业务分发”混在一起了。

你当前代码里最需要拆的点

我看过你现在的 `readPump`，这段几乎就是“全栈”：

- `receiveMessage`
- `tlv.Deserialize`
- `fn.Action`
- `s.HandleFn`
- `handler.OnData`

这部分应该抽离成一个统一的 dispatcher。

推荐接口设计

下面这个接口大概就是你要的“连接层抽象”：

```go
package transport

import (
	"context"
	"net/http"
)

type Session interface {
	ID() string
	Send(ctx context.Context, payload []byte) error
	Read(ctx context.Context) ([]byte, error)
	Close() error
}

type ServerTransport interface {
	Listen(ctx context.Context, addr string, opts ...any) error
	Serve(ctx context.Context) error
	Close() error
}

type ClientTransport interface {
	Dial(ctx context.Context, addr string, opts ...any) (Session, error)
	Close() error
}

type ProtocolFactory interface {
	NewServer() ServerTransport
	NewClient() ClientTransport
}
```

然后再拆一层协议：

```go
package codec

type Envelope struct {
	Kind     EnvelopeKind
	Action   uint8
	ID       uint64
	Body     []byte
	Raw      []byte
	Meta     map[string]string
}

type EnvelopeKind int

const (
	KindRPC EnvelopeKind = iota + 1
	KindData
)

type Codec interface {
	Decode(raw []byte) (Envelope, error)
	Encode(env Envelope) ([]byte, error)
	Detect(raw []byte) bool
}
```

然后是分发器：

```go
type Dispatcher interface {
	Dispatch(ctx context.Context, sess transport.Session, env codec.Envelope) error
}
```

核心分发逻辑就会变成：

```go
func (d *DefaultDispatcher) Dispatch(ctx context.Context, sess transport.Session, env codec.Envelope) error {
	if env.Kind == codec.KindRPC {
		return d.dispatchRPC(ctx, sess, env)
	}
	return d.handler.OnData(ctx, sess, env.Raw)
}
```

真正的路由逻辑：

```go
func (d *DefaultDispatcher) dispatchRPC(ctx context.Context, sess transport.Session, env codec.Envelope) error {
	switch env.Action {
	case actions.ACTION_CALL:
		// 1. 解析方法名/参数
		// 2. 查本地 serviceMap
		// 3. 没有就 CallNetFunc
		// 4. 有就 CallFunc
		return nil
	case actions.ACTION_REPLY_SUCCESS, actions.ACTION_REPLY_ERROR:
		// 处理 reply channel / rpcResult
		return nil
	default:
		return nil
	}
}
```

然后 `handler.OnData` 只负责“非 @FN 的原始业务数据”，不要再知道 `fn` 编码细节。

我建议你把当前结构调整成这样的层次

- `sloth.Connect`
  - 只负责协调
  - `Register`
  - `Listen`
  - `Dial`
  - `Serve`

- `transport/ws`
  - `WsServer`
  - `WsClient`
  - 只负责 socket 收发，不负责业务判断

- `codec/fn`
  - `@FN` 编解码

- `dispatch`
  - `DefaultDispatcher`
  - `dispatchRPC`
  - `dispatchData`

- bucket / `room`
  - 继续保留
  - 但不参与协议解析

这就基本达到了你想要的“只写一个 ws，然后以后能扩其他协议”。

我建议你把一句话原则定下来

- 传输层只负责“字节流”
- 协议层只负责“帧解析”
- 连接管理层只负责“会话、桶、房间”
- 业务层只负责“服务调用 / data handler”

如果这四层分开，后面加 tcp/quic/kcp 时，改动范围就非常小。

你现在“删掉 tcp/kcp”其实是对的，因为只保留 ws 后，复杂度会明显下降。然后再把抽象能力补上，才是正确的前进方向。

我建议的最小落地方案

不是先重构一大版，而是先做三步：

1. 把 `HandleFn` 从 ws_server.go / ws_client.go 抽到单独 `dispatch` 包
2. 把 `fn` 判定和 `OnData` fallback 也放到 `dispatch`
3. 把 `Connect.Listen` 里的 `ws` 创建逻辑收口成 `transport.Factory`

也就是一句话：先把“读循环中所有业务判断”抽出来，不要继续让 ws 实现类干所有活。
