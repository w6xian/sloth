v4.1.1：一个 `Connect` 同时监听 ws / tcp / quic（多协议）。

## 一、原来为什么不行（两个坑，均已实测复现）

**坑 1：给 QUIC 配 TLS 会把 ws/tcp 端口一起变成 TLS**
`makeListenerFor` 只看 `Connect.tlsConfig != nil` 就 `tls.Listen(...)`。而 QUIC 强制要求 tlsConfig → 一旦为 QUIC 配证书，ws/tcp 的明文客户端全部握手失败（实测：`client sent an HTTP request to an HTTPS server`，没有任何报错）。

**坑 2：服务端推送只覆盖最后一条协议**
`Listen` 每次都直接 `c.client.setServe(srv)` 覆盖 `ClientRpc.Serve`。实测三条协议时 `getServe()` 只剩 `*quic.QuicServer` —— 先注册的协议照样收包、照样能调用服务端，**但永远收不到 `Call`/`CallRoom`/`CallBucket`/`Broadcast` 推下来的消息**，且不报错。

**坑 3：三条链路被登记成同一个 userId**
`v1.Sign` 靠入参区分协议，而三个 example 客户端传的都是 `[]byte("sign")`——服务端一个也认不出，三条链路全部落到兜底 `userId=99`。推送其实扇出到了三条链路，但日志里全是同一个 userId，**看不出消息到底推给了谁，看起来像只有一条链路在线**。

修法：协议标识不该由业务传。库在每次调用时把 `sloth-protocol`（`sloth.HeaderProtocol`）写进固定头，取值就是 `Dial` 时的 network；服务端用 `sloth.GetProtocol(ctx)` 读。客户端代码零改动，业务也改不了这个值（写在最后，覆盖手填）。

## 二、改动（对外接口零变化）

| 文件 | 改动 |
|---|---|
| `listener.go` | 是否套 TLS 交给传输自己：ws/tcp 明文监听，wss 走 `ServeTLS`、QUIC 走 quic-go 内部 |
| `connect.go` | `serveInstance()`：单协议返回原实例（类型不变），多协议返回合成实例；`Serve()` 支持 wss 用 `WithTLSConfig`；关闭时的 `net.ErrClosed` 不再当故障上报；**调试端口起不来只告警，不再拖垮整个服务** |
| `multi_server.go`（新） | `multiServer` 合成实例，实现 `types.IServer`，`Rooms`/`AllBuckets`/`Broadcast` 跨传输扇出，额外提供可选能力 `ChannelOf` |
| `call_client_func.go` | 新增 `serverChannel()`：`Call`/`CallNet`/`CallWithHeader`/`Channel` 走 `ChannelOf` 跨传输查连接；单协议行为完全不变 |
| `nrpc/stream/channel.go` | 新增客户端侧身份 `SetLocalAuth`：让 tcp/quic 客户端方法里的 `GetAuthInfo()` 与 ws 行为一致（见第四节） |
| `nrpc/tcp`、`nrpc/quic` | `SetAuthInfo` 把身份同步到当前连接；建连接时补写已存身份 |
| `const.go` | 新增固定头键 `HeaderProtocol`（`sloth-protocol`） |
| `call_server_func.go` | `ServerRpc` 记下 `Dial` 的协议名（与 `Listen` 同锁），`callHeader` 在**最后**压上 `sloth-protocol`（业务手填会被覆盖） |
| `call_client_func.go` | 新增 `GetProtocol(ctx)`：服务端读对端协议，取不到返回 error 而非"默认协议" |
| `connect.go` | `Dial` 连协议名一起登记（`setListen(call, network)`） |

## 三、案例 `examples/multi`

- `examples/multi/main.go`：一个 `Connect` 同时 `Listen` ws:8990 / tcp:8991 / quic:8992，共用同一份注册表，每 5 秒 `CallRoom` 推送
- `examples/multi/client/main.go`：三条协议各连一条，每 2 秒调用

**端口刻意与三个单协议 example 服务端保持一致**，因此 `examples/ws/client`、`examples/tcp/client`、`examples/quic/client` 不用改一行代码就能直接连 multi 服务端——验证多协议时可以直接拿它们当客户端。

（顺带修了 `examples/tcp/client`、`examples/quic/client` 的地址：原来写 9091/9092，与自己的服务端 8991/8992 对不上。）

## 四、验证：multi 服务端 + 三个独立客户端

```
go run ./examples/multi            # 8990(ws) / 8991(tcp) / 8992(quic)
go run ./examples/ws/client        # 连 8990
go run ./examples/tcp/client       # 连 8991
go run ./examples/quic/client      # 连 8992
```

三个客户端**零改动**跑通，实测结果：

| 项 | ws | tcp | quic |
|---|---|---|---|
| 握手 / Sign（`roomId=1`） | ✅ userId=1 | ✅ userId=2 | ✅ userId=3 |
| 调服务端 `v1.Test` | ✅ | ✅ | ✅ |
| 收到服务端 `CallRoom` 推送（`shop.Test`） | ✅ | ✅ | ✅ |
| 客户端方法里 `GetAuthInfo()` 能拿到自己的身份 | ✅ | ✅ | ✅ |

三条链路的推送日志共用同一个服务端 trace（如 `5f691c-23008-3`），且客户端侧读到的 userId 分别是 1 / 2 / 3，说明一次 `CallRoom` 确实扇出到了三条协议、且各自身份没串。

服务端 Sign 日志：

```
client signed proto=ws   from=header userId=1 roomId=1
client signed proto=tcp  from=header userId=2 roomId=1
client signed proto=quic from=header userId=3 roomId=1
```

`from=header` 表示协议标识来自库自动写入的固定头，不是业务入参（三个客户端传给 Sign 的仍然都是 `"sign"`）。

第 4 行是这次验证逼出来的改动：客户端方法里调 `ch.GetAuthInfo()`，ws 能拿到（连接自带身份），tcp/quic 拿不到（`stream.Channel` 的身份只有服务端语义那套，客户端侧恒为 0，报 `user id is 0`）。同一个业务方法换传输就换行为，已修平。
