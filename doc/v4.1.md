## 效果（同机对比，基线 = 你提交的 P0 commit，用 git worktree 跑的）

| 场景 | 改前 | 改后 | 提升 |
|---|---|---|---|
| 同连接串行调用 | 267,371 ns/op | **69,556 ns/op** | **3.8x** |
| 同连接 20 并发调用 | 478,631 ns/op | **13,748 ns/op** | **35x** |
| 并发吞吐 | 48,759 次/3s | **253,048 次/3s** | **5.2x** |
| 每调用分配 | 5,399 B / 79 allocs | 5,043 B / 74 allocs | -7% |

关键信号：改前并发比串行还**慢**（478k vs 267k）——这是"单连接全程持锁串行"的典型特征；改后并发延迟是串行的 1/5，锁真的没了。

## 改了什么

**1. per-call 回包分发，去掉全程锁（`nrpc/conn.go`）**

`SendData` 原实现从发请求到收回包一直握着 `cc.Lock`，且所有调用共用一个 `PRpcResult` 队列——并发时调用者会读到别人的回包并丢弃，所以当初只能串行。现在：

- `pending map[uint64]chan []byte`：每个 callId 一个容量 1 的回包通道，回包直达等待者；
- `SendData` 完全不加锁，同连接可并发任意多个调用；
- `callId` 改为连接内 `atomic` 自增，摘掉全局 snowflake 锁；
- 连接关闭时 `CloseCalls()` 唤醒所有等待者（否则要干等 10s 超时）。

顺带消除了"回包队列满阻塞 readPump 10 秒"的队头阻塞——`Receive` 现在是非阻塞投递，永不卡住读循环。

**2. handler 移出 readPump（新增 `nrpc/wsocket/ws_dispatch.go`）**

readPump 只做解码+投递，业务执行交给 worker 池：

- 连接按 `shard` 固定绑定到某个 worker → **同一连接严格保序**，不同连接并行（业务无感）；
- 每 worker 队列有界（默认 256），满了阻塞投递形成背压，不丢 RPC 请求（丢了调用方只能干等超时）；
- worker 内单独 recover：业务 handler panic 不再击穿整个进程，有 `sloth_ws_dispatch_recovers_total` 计数。

**3. 队列容量可配置 + 背压指标**

`option.WithChannelQueueSize(n)`（服务端/客户端都生效，走 `SetChannelQueueSize` 可选接口），配套 `sloth_ws_queue_full_drops_total`。原来 10/5 是硬编码的。

**4. 修了第三方 tlv 库的并发 bug**

`tlv.newOption()` 返回**全局共享**的 option 对象并往里写字段——多 readPump 并发解析直接数据竞争 + 互相污染编码状态。加了 `tlvMu` 串行化，并给 FN 帧加 magic fast-path（绝大多数消息不用进锁）。

顺带：fuzz 抓到我第一版 `Unlock` 写在 panic 路径上（tlv 对畸形输入 panic）→ 锁永久持有 → 后续全部死锁 600s。已改 `defer` 解锁。**这是这轮 fuzz 第二次立功。**

**5. 顺手修了一个正确性问题：房间广播跨分片漏人**

连接按 `userId` 分桶，同一房间的成员通常落在不同桶，每个桶各有一个同 `roomId` 的 Room；而 `Room(roomId)` 只返回**第一个**分片 → `CallRoom` / 房间广播只推给部分人（表现为"有人收不到"）。新增 `WsServer.Rooms(roomId)` + `serverRooms()` helper，`CallRoom` 和 `Room()` 改为覆盖所有分片（不支持的实现退化单结果）。加了回归测试 `TestRoomAcrossBucketShards`。

## 没做的三项，及原因

- **入口 header 池化**（`connect.go:513` 每次 `make` 一个 map）：技术上很简单，但 header 会被塞进 ctx，业务常把 ctx 传给异步 goroutine，池化后可能读到被复用的脏数据——这类 bug 极难排查。收益（一次 map 分配）不值得冒这个险。
- **分片改 binary 帧（去 base64）**：JS 客户端侧要同步改，属于协议变更，风险高于收益，建议单独排期。
- **metrics 采样**：`Observe` 约 50-100ns，相比现在 70μs/调用不值得改；等调用耗时降到 10μs 级再说。

## 提醒

- C 盘只剩几十 MB，`-race` 编译会直接失败（我全程把 `TMP/GOCACHE` 指到 `D:\var\tmp` 才跑通）。建议清一下，否则日常开发会随机踩到。
- `bucket` 的 `TestBucketBroadcastRoomQueueFull` 在 5 个包并行跑时会偶发失败（单跑稳定）——它依赖"队列满"的时间窗，CPU 争抢时打不中。建议后面改成用显式容量 + 阻塞点同步，而不是 sleep 等时序。
