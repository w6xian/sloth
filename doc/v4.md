## 先说判断

这个项目的**抽象立意是对的**——双向 RPC（服务端能按 userId/room 反调客户端）+ 长连接管理（bucket/room）+ 统一传输入口，这套组合在市场上不多见，方向没问题。但目前的状态是：**功能跑通了，工程化和性能都还停在"能跑"，离"高性能/高复用"差一个量级的改造**。最要命的两处：单连接 RPC 是串行的，客户端读循环没有 recover。

## 优点（真的有，不是客套）

1. **双向 RPC 抽象干净**：`ServerRpc`/`ClientRpc` 两个方向共用同一套 `Call/CallWithHeader`，对外只有 `DefaultClient/DefaultServer + ClientConn/ServerConn`，心智负担小。这是我一开始读反了但语义自洽的设计。
2. **传输层抽象留了口子**：`protocol_runtime.go:15` 的 `ProtocolFactory` + registry，加 tcp/quic 不用侵入 ws 逻辑。
3. **连接管理有设计**：bucket 按 CPU 分片，`b.chs` 是 user→channel 唯一映射，`RangeChannels` 天然去重（`bucket/bucket.go:163`）——全服推送不会重复调用同一连接，这个坑很多人会踩。
4. **有性能文化，不是拍脑袋**：手写零反射 JSON（`nrpc/conn.go:50`）、codec/header 池化、`bucket.go:142-143` 注释里还留了"池化 3.06ms vs 新建 1.39ms"的实测数据。这种"先测再定"的习惯很值钱。
5. **可观测性齐活**：trace 全链路、Prometheus metrics、pprof、连接数/单 IP 限制、Origin 校验。
6. **测试不是摆设**：21 个测试文件、22 个 benchmark、`connect_test.go` 是真起服务+客户端的 e2e。

## 缺点（按严重度）

### 一、能不能上生产级别

- **客户端 readPump 的 recover 被注释掉了**（`nrpc/wsocket/ws_client.go:531-535`）。服务端同名函数有 recover，客户端没有——收到任何畸形帧，客户端进程直接崩。这不是"待优化"，是漏洞。
- **库 API 直接 panic**：`ws_client.go:84` `SetServerHandleMessage` 的实现是 `panic(...)`。库不该用 panic 表达"未实现"，应返回 error。
- **解码路径可被构造输入打崩**：`decoder/frame/slice.go:162-180` 校验 `len(b)>=7` 后去读 `b[5:9]`，7~8 字节的恶意帧越界；`decoder/ag/ag.go:29` 用 `1<<16` 判 uint16 上限（差一）；`slice.go:182` 的 `int(headerSize)+int(l)` 在 32 位平台可绕过长度校验；外部 tlv 库解析不可信字节全程无 recover（`ws_server.go:595`、`ws_client.go:596`）。
- **反射参数只校验上限不校验下限**（`internal/ref/func.go:169-184`）：报文里 args 少于签名就 panic，全靠 `connect.go:467` 的 recover 兜底——兜得住但连接已断。
- **错误不可判定**：全库裸 `errors.New`，调用方分不清"超时/连接关闭/队列满/业务错误"，也就没法写重试。
- **连接泄漏**：`bucket.go:230-233` 先入表再 `room.Join`，Join 因 Drop 失败则连接残留；`Logout` 把 `UserId` 置 0 后 `bucket.go:281` 按 id 删除会漏删。

### 二、性能天花板（"高性能"目标下最致命的）

- **单连接 RPC 全程持互斥锁**：`nrpc/conn.go:65-67`，`SendData` 从发请求到等回包一直握着 `cc.Lock`。同一条连接上所有调用**严格串行**，QPS 上限 = 1/RTT。浏览器只有一条 ws 连接，这个设计直接把并发能力锁死在 RTT 上。这是全项目收益最大的一个改动点。
- **回包队列满会阻塞 readPump 10 秒**（`conn.go:79-91`）：队头阻塞，一个慢调用拖死整条连接的入站。
- **业务 handler 在 readPump 内联执行**（`ws_server.go:599-614`）：慢 handler 阻塞该连接所有入站消息，且无背压。
- **callId 走全局 snowflake 锁**（`conn.go:53`）：callId 只需连接内唯一，却付了全局锁代价。
- **高频路径开销**：每调用一次 metrics 直方图观测（`nrpc/utils.go:60-64`）；每帧 base64（+33% 体积）；每帧 `json.Unmarshal` 解分片；每个 struct 参数一次 `json.Unmarshal`、返回值一次 `json.Marshal`（`internal/ref/func.go:133`、`internal/utils/utils.go:53`）。
- **广播路径**：`Room.Broadcast` 持 `rLock` 遍历并 `Push`，成员慢会卡住 Join/Leave（`room.go:156-166`）；`Room()` 跨桶 O(桶数) 线性扫描（`ws_server.go:312-322`）。

### 三、架构与一致性（拖累"高复用"）

- **双实现并存**：decoder 有三套（`ag`/`fn`/`frame`）、codec 两个入口（`GetCodecer` vs `UseCodec`）、dispatch 两份（`nrpc/dispatch.go` vs `internal/transport/dispatch.go`）、header JSON 编码两份。**每加一个特性要写两遍，每修一个 bug 要修两处**——我今天踩的 trace 漏改就是这个病。
- **死代码与注释失真**：`wsocket/utils.go:54` 的 `getSliceName`、`slice.go:205` 的 `serialize` 已成孤儿；`nrpc/transport.go:52-55` 写的帧格式与 `message/header.go:94-109` 实际不符；`ws_server.go:461` 注释与代码不一致。
- **模块名 `v3` 与目录 `v4` 不一致**，README 里还挂着 v2 路径的示例链接。（v4.0.0 已修：module 路径统一为 v4，示例链接改为相对路径）对外发布时会让人怀疑版本。
- **ctx 形同虚设的地方**：`bucket.go:146` `BroadcastAll(ctx, ...)` 的 ctx 完全没用，调用方传的超时/取消对全服广播无效。

## 建议的调整（按投入产出排序）

**只做三件事的话：**
1. 去掉单连接串行锁（性能天花板）
2. 客户端 recover + 解码边界收口（能不能上生产）
3. 收敛 decoder/codec/dispatch 双实现（后面所有工作量减半）

### P0 正确性（1~2 周）

1. 客户端 `readPump` 补 recover；`panic` 改 error；解码边界统一收口（长度校验 `>=`、32 位改 uint64 中间量、TLV/frame/ag 入口加 recover）。
2. 反射参数补下限校验；`internal/utils/json.go:144-152` 断言带 ok。
3. 建 sentinel 错误：`ErrTimeout / ErrConnClosed / ErrQueueFull`，用 `%w` 包裹，让调用方能判定重试。
4. 修 bucket 注册/Join 顺序与 Logout 漏删；`Connect.Close` 等 http goroutine 退出。
5. **给解码器写 fuzz**（frame/ag/fn/header）——这是唯一直接吃不可信输入的层，fuzz 是这里性价比最高的投入，大概率还能再挖出几个越界。

### P1 性能（核心改造）

1. **per-call 并发化**：`RpcChannel` 改成 `map[callId]chan` 回包分发表（配 RWMutex 或分片），去掉 `SendData` 的全程锁。同连接并发 N 个调用，QPS 从 1/RTT 变 N/RTT。
2. `callId` 改连接内 `atomic.Uint64`，摘掉全局 snowflake 锁。
3. **handler 移出 readPump**：入站解码后投到有界 worker 池，队列满有明确策略（丢弃/降级并计数），顺带解决背压。
4. 写队列容量 10 → 可配置，满时按策略处理并暴露 drop 指标（现在已有 `dropped` 计数的雏形，推广到所有推送路径）。
5. 每调用分配治理：服务端入口 header 走池（我今天做的 `callHeader` 覆盖调用侧，`connect.go:498-500` 那一处还没覆盖）；返回值编码照 `MarshalJSONFast` 的先例改手写；分片走 binary 帧去掉 base64。
6. metrics 观测改 1/N 采样 + 计数器补偿。
7. `roomId → bucket` 加索引，消掉跨桶线性扫描。

### P2 复用与架构

1. **收敛双实现**：decoder 三选一、codec 单入口、dispatch 单一实现，删死代码与重复常量。做完这步，新增特性的改动量从"两处"降到"一处"，才是真正的"高复用"。
2. **用第二协议验证抽象**：真正落地一个 tcp 传输。`ProtocolFactory` 目前只有 ws 一个实现，抽象没被第二个实现检验过——通常第一版抽象会在第二个实现时暴露问题。
3. 统一 module 路径与文档（v3/v4、README 的 v2 链接）。
4. 补测试盲区：`decoder`(根)、`option`、`types`、`internal/transport`；把 `e2e_bench_test.go` 升级成带断言的功能 e2e（现在它只报吞吐不校验正确性）。
5. ctx 端到端接上，别让 `BroadcastAll(ctx)` 这类形参继续做摆设。

---

一句话总结：**优点在抽象与"敢实测"的习惯上，缺点集中在"单连接串行 + 解码边界 + 双实现并存"三处**。前两个决定它能不能扛生产和多快，第三个决定后面每件事要做两遍。建议按 P0 → P1(1)(3) → P2(1) 的顺序推，其余可以边用边补。
