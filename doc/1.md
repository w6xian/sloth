## 一、你的怀疑：对了一半，但当前代码已修过"顶号残留"

你怀疑"断线重连后前一个连接没断干净、残留在 bucket"。这个方向正是这个仓库历史里修过的问题（见 `bucket/bucket.go` 和 `ws_server.go` 里大段注释），当前代码对**"同一 userId 再次登录（顶号）"**已经做了处理：

- `Bucket.Put` 发现同 userId 已有旧连接时：旧连接先退出房间、`ch0.Close()` 关掉、从 `b.chs` 删掉，再挂新连接（`bucket/bucket.go:150-165`）。
- `DeleteChannel` 有 `cur == ch` 保护：旧连接晚到的清理不会误删已顶号的新连接（`bucket/bucket.go:227`）。
- 服务端 `readPump` 退出时无条件 `DeleteChannel`（`ws_server.go:452-464`），不再放过已登录连接。
- `smap.Reg(name)` 幂等，同服务名重登拿到同一个 `svrId`（`smap.go:55-68`）。

所以：**只要重连后客户端真的重新调用了登录/注册 RPC，bucket 最终一定收敛到新连接上**，不存在"顶号不干净"的永久残留。真正的问题在下面两个环节。

## 二、真正的问题（弱网场景下）

时间线是这样的：

**1. 客户端弱网 → TCP 半开（客户端没发 FIN，直接不可达/被 NAT 踢掉）**

**2. 服务端发现死连接很慢（最长约 PongWait）**

服务端 `readPump` 靠 `ReadMessage` 阻塞 + PongWait 读超时来感知断线：

```452:471:nrpc/wsocket/ws_server.go
	defer func() {
		...
		GetBucket(ctx, s.Buckets, ch.UserId()).DeleteChannel(ch)
		...
		ch.Close()
	}()
	...
	ch.Conn.SetReadDeadline(time.Now().Add(s.PongWait))
	ch.Conn.SetPongHandler(func(string) error {
		ch.Conn.SetReadDeadline(time.Now().Add(s.PongWait))
		return nil
	})
```

默认 `PongWait=54s`、`PingPeriod≈49s`。客户端网络一断、pong 不再到达，服务端要等约 54s 才在 `readPump` 报错并执行 defer 里那句 `DeleteChannel`。**这 54s 内，bucket 里该 svrId/userId 仍然指向旧（已死的）连接**，服务端这时调客户端（`ClientRpc.Call` → `Bucket.Channel(svrId)` → 写旧连接）要么挂到 WriteWait 超时，要么报错。

**3. 客户端自动重连成功，但不会自动重新登录——这是卡死的最可能根因**

客户端 `LocalClient` 断线后确实会 `KeepAlive` 自动重连（1-30s 重试，`ws_client.go:215-217`），但**每次连接都是全新状态**：

```198:218:nrpc/wsocket/ws_client.go
	wsConn := NewWsChannelClient(c.Connect)
	...
	wsConn.Conn = conn
	wsConn.RoomId = 0
	...
	go c.readPump(ctx, wsConn, closeChan, resp)
	go c.writePump(ctx, wsConn, closeChan)
	<-closeChan
	cancel()
	// 重连
	if c.KeepAlive && parentCtx.Err() == nil {
		c.ListenAndServe(parentCtx)
	}
```

- 新连接是全新的 `WsChannelClient`，UserId/认证信息**全部清零**；
- 框架**没有**"用上次的 AuthInfo 自动重新认证/重新注册"的逻辑；
- 登录（`v1.Sign`/`v1.Reg` → `Bucket.Put`）是**业务一次性 RPC**，示例里只在启动时调一次（`examples/ws/main.go` 的 `Reg`/`Sign`）。

于是客户端弱网重连后：
- 服务端新连接没人注册 → bucket 里该 svrId 仍指向旧连接；等 54s 旧连接被清掉后，**bucket 变成空条目**；
- 新连接永远没被 `Put` 进去 → 服务端调客户端永远 "channel not found" / 打到旧连接。

**"重启任一端都能好"恰好印证了这一点**：重启客户端会强制重跑"连接→登录→注册"；重启服务端清空 bucket 后，客户端重连（若业务绑定了 OnReady 重登）会重新注册。

## 三、处理建议

### 1. 业务层（最直接、最必要）
把"登录/注册"做成一个**幂等函数**，不要只在启动时调用一次，而是在每次连接建立成功的回调里都调用（服务端侧 `smap.Reg` + `Bucket.Put` 都幂等，重复调用安全、会自动顶号）：

```go
func (h *Handler) OnReady(ctx context.Context, resp *http.Response, c *sloth.Connect, ch bucket.IChannel) error {
    // 每次(重)连都重新注册：同服务名 → 同 svrId → 服务端 Put 自动顶掉旧连接
    _, err := h.login()   // 内部: client.Call(ctx, "v1.Reg", name) 等
    return err
}
```

注意两点：
- 登录必须用**当前连接**发起（走 `c.Client()`/每次 OnReady 传入的 channel），不要缓存启动时拿到的旧句柄/旧 ctx；
- 登录成功后再对新连接重新 `SetAuthInfo`（因为重连后是新 `WsChannelClient`，auth 是空的）。

### 2. 调小心跳，缩短服务端"残留窗口"
服务端默认要等 ~54s（PongWait）才清死连接。可以用 `WithPingPeriod` / `WithPongWait` / `WithWriteWait`（`connect_options.go:61-82`）调小，比如服务端 `PongWait≈15-20s`、`PingPeriod≈10s`。这样断线后 bucket 里的脏连接最多残留十几秒，配合客户端快速重连重登，基本能在 1~2 个心跳周期内自愈。

### 3. 框架层（可选改造，让这类问题彻底不再依赖业务自觉）
- **客户端自动恢复会话**：在 `LocalClient` 里保存最后一次成功的 `AuthInfo`，每次 `ClientWs` 建好新连接后自动用该 AuthInfo 重新发起一次登录/注册（或新增一个 `OnRelogin` 回调供业务挂重登逻辑）；
- **调用侧兜底**：`Bucket.Channel()` / `Call` 返回不到 channel 或超时，就地检查 `ch.Closed()` 懒删除并尽快返回明确错误（"channel not found"），而不是长时间阻塞，避免业务误以为连接还在；
- **连接级去重提示**：`ListenAndServe` 每次重连都重新生成 `app_id`（`ws_client.go:128`），如果你们服务端有按 app_id 去重/路由的逻辑，弱网换 IP 重连会把它当成"新客户端"，旧连接的应用层状态可能不会被踢掉——需要确认服务端是按 `userId/svrId`（Put 顶号）而不是按 app_id 管理连接。

### 4. 排查验证（先确认根因再动手）
打日志确认三件事：
1. 客户端重连后，是否真的重新发出了 `Reg/Sign`（在重连回调里打日志）；
2. 服务端 `Put`/`DeleteChannel` 是否被触发、`b.chs[svrId]` 是否换成了新连接（临时在 `bucket.Put` 加日志）；
3. 失败时具体错误是 `channel not found`（没注册）还是写超时/断 pipe（打到了旧连接）——前者指向"没重登"，后者指向"心跳太慢导致旧连接残留期过长"。
